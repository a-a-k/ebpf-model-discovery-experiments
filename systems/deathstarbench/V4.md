# DeathStarBench iteration-4 operation contract

The application is pinned to DeathStarBench commit
`6ecb09706140f8730b5385c08f1386c654c3c526`. This document describes
requirements of the fixed requests in `experiment_v4.py`. It supplies identical
semantic knowledge to all observation arms. It does **not** provide discovery
edges: each declared call must resolve to an actual, unambiguous recovered edge,
or the graph prediction is unavailable.

| Operation and entry route | Required calls before the HTTP response | Conditional behavior |
| --- | --- | --- |
| `compose_post`, `POST /wrk2-api/post/compose` | nginx → ComposePost; ComposePost waits for Text, User, Media and UniqueId, then PostStorage write, UserTimeline write and HomeTimeline write. UserTimeline writes its MongoDB, then Redis. For the fixed user 0 input, HomeTimeline obtains followers from SocialGraph and updates its Redis. | Media content varies by attempt, but ComposePost still waits for its Media future. The later owner/follower timeline probes are external postconditions, not compose graph edges. |
| `read_home_timeline`, `GET /wrk2-api/home-timeline/read?user_id=3&start=0&stop=10` | nginx → HomeTimeline; HomeTimeline reads its Redis and calls PostStorage.ReadPosts. | The controlled user-timeline MongoDB is off the read path. |
| `read_user_timeline`, `GET /wrk2-api/user-timeline/read?user_id=2&start=0&stop=10` | nginx → UserTimeline; UserTimeline reads its Redis and calls PostStorage.ReadPosts. | UserTimeline queries MongoDB only when Redis supplies fewer than ten post IDs; this is not an unconditional required edge. |

The compose handler launches several futures, but obtains their results before
returning. `std::launch::deferred` on the timeline writes means execution starts
when the handler calls `get()`, still before the acknowledgement. The Lua route
returns its successful body after this handler returns. Source:
[ComposePostHandler](https://github.com/delimitrou/DeathStarBench/blob/6ecb09706140f8730b5385c08f1386c654c3c526/socialNetwork/src/ComposePostService/ComposePostHandler.h),
[compose Lua route](https://github.com/delimitrou/DeathStarBench/blob/6ecb09706140f8730b5385c08f1386c654c3c526/socialNetwork/nginx-web-server/lua-scripts/wrk2-api/post/compose.lua),
[UserTimelineHandler](https://github.com/delimitrou/DeathStarBench/blob/6ecb09706140f8730b5385c08f1386c654c3c526/socialNetwork/src/UserTimelineService/UserTimelineHandler.h),
[HomeTimelineHandler](https://github.com/delimitrou/DeathStarBench/blob/6ecb09706140f8730b5385c08f1386c654c3c526/socialNetwork/src/HomeTimelineService/HomeTimelineHandler.h).

The adapter registers users 0–3, arranges follower 1→0 and 3→2, and creates one
stable post for user 2. That post is checked in user 2's and follower 3's
timelines before traffic. The fixture may be present in Redis; a MongoDB outage
therefore cannot be assumed to break every user-timeline read. The independent
outcome is the **complete** HTTP status and body: exact compose acknowledgement,
or JSON timeline shape with the stable fixture text. A live graph path predicts
only that required connectivity is present. It does not prove correct payload,
cache contents, transaction outcome, or finite response time.
The optional owner/follower verification reads only the newest 1,000 posts.
An exact marker in both complete pages proves the postcondition; absence from
either bounded page is unknown because later posts can displace it.

`CONTROLLED_SERVICE_ALIASES` names the logical UserTimeline service. The two
physical replica containers and MongoDB container are separately identified by
`selected_inventory()`, from deployment facts, never inferred from graph node
names. The controlled state is 11/10/01/00 for replica a/b; the selected database
fault stops `dsb-user-timeline-mongodb` on guest a. A graph that collapses the
replicas cannot by itself distinguish a and b. Endpoint attachment requires
observed identity evidence; an unmatched inventory entry cannot insert a node.

V4 primary requests have one declared step and one deterministic opaque request
ID. The parent runner commits `plan_operation()` before dispatch. HTTP starts
and terminal receipts are journaled independently by `transport_v4`. An
incomplete transport has unknown business outcome. There is no experiment HTTP
deadline, response-time success threshold, or temporal span-admission gate.
V4 removes the adapter's injected HAProxy connect/client/server timeouts while
leaving the historical adapter and upstream application behavior intact. The
inherited deployment readiness check is overridden only for its replica probes:
bounded direct HTTP checks remain technical preparation evidence and do not
call or score `operation()`.
