# OpenTelemetry Demo iteration-4 contract

`experiment_v4.py` subclasses the historical adapter; it does not change the
v1--v3 workload or its saved results.  The v4 workload precomputes stable attempt
and request IDs, and the orchestrator commits that plan before dispatch.  Every
HTTP call uses `ebpf_discovery.transport_v4` with the durable campaign journal.
There is no experiment HTTP timeout, observation cutoff, or timestamp admission
gate.  An incomplete call and every undispatched suffix step remain unknown and
`not_attempted`; neither is converted into an HTTP failure.

The generated product-catalog Envoy router retains round-robin routing and its
active gRPC health checks, but v4 replaces the adapter-added two-second route
deadline with `timeout: 0s`, Envoy's documented way to disable that deadline,
and removes the adapter-added half-second connection deadline.  The remaining
half-second Envoy health-check timeout controls endpoint health classification,
not an application request deadline.  With `connect_timeout` omitted, Envoy
applies its native five-second connection default.  These facts are recorded in
adapter metadata rather than presented as experiment observation gates.  Docker
health-check and process-control timeouts are technical readiness guards.  In the
pinned source, the audited frontend gRPC gateway calls do not pass per-call
deadlines, checkout's gRPC calls inherit the incoming context without adding a
deadline, and checkout constructs an `http.Client` with an instrumented
transport but no `Timeout`.  Library, operating-system, and frontend-proxy
defaults remain native behavior and must be reported separately from experiment
and readiness controls; v4 does not rewrite them.

Envoy documents zero as disabling the route deadline and the omitted connection
field's native default in its API references for
[`RouteAction.timeout`](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/route/v3/route_components.proto)
and [`Cluster.connect_timeout`](https://www.envoyproxy.io/docs/envoy/latest/api-v3/config/cluster/v3/cluster.proto.html).

## Declared semantics, not recovered topology

`CONTRACTS` contains the pinned-source audit used equally for native, eBPF, and
combined observations.  It declares ordered external steps, frontend aliases,
and mandatory call obligations.  Exact operation strings are matcher hints, not
authority to add an edge.  The resolver must match every obligation to a unique
edge already present in the source-local Bering graph.  A missing or ambiguous
match makes that prediction unavailable.  Static aliases, the two catalog
placements, and the catalog PostgreSQL mapping are inventory with explicit
provenance; they do not create graph nodes or edges.

For the fixed USD inputs:

- browse requires frontend -> product-catalog -> catalog PostgreSQL;
- add-to-cart first requires browse, then Cart `AddItem` and `GetCart`, including
  their Valkey state;
- checkout first requires browse and add-to-cart, then checkout's cart read,
  catalog pricing, currency conversions, shipping quote and shipment, payment,
  and frontend catalog enrichment.

Checkout's `EmptyCart` and mock-email calls are attempted but their errors are
ignored by the pinned service, so they are not mandatory success obligations.
Kafka delivery and accounting persistence are also not prerequisites for the
immediate HTTP acknowledgement.  They form a separate recovery observation.

## Async recovery

Stopping accounting no longer reserves or sleeps through a deadline.  While it
is stopped, `observe_async` performs one independently timestamped SQL snapshot
for each actual returned order ID.  Missing rows are `pending`, not evidence of
Kafka delivery and not failure.  The orchestrator then starts accounting and
calls `verify_async` for those same IDs; each call performs one uncapped-policy
snapshot and reports exact persistence, definitive persisted-payload mismatch,
pending, or unavailable evidence.  Repetition and the platform technical stop
belong to the orchestrator.  The adapter never waits for persistence while the
consumer remains paused and never turns elapsed time into a business outcome.
